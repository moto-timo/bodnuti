# Lessons from OE review history

Distilled by zai-org/GLM-5.3 from 508 changelogs of resent patches on openembedded-core, openembedded-devel, 2023-01-01 to 2026-01-01.

- Set an accurate Upstream-Status on every patch (with the upstream submission/issue URL), keep it consistent across the series, and update it when the situation changes (e.g. Submitted -> Backport).
- Prefer upgrading to a release containing the fix, or backporting the upstream-accepted patch, over carrying local workarounds; fix problems at their root cause, not in dependents.
- Remove patch fuzz and refresh patches against the version actually being patched so they apply cleanly; drop patches already applied upstream.
- Keep series bisectable: order commits so each builds, split large changes into one logical change per patch, and drop unrelated changes.
- Add the runtime dependencies (RDEPENDS) packages actually need, especially for ptest scripts and tools (e.g. coreutils/printenv), and remove redundant or defensive dependencies.
- Use PACKAGECONFIG for optional features with sensible defaults, add negative conditions so upstream defaults don't quietly enable options, and gate services, init files and ptest inclusion on the corresponding PACKAGECONFIG/DISTRO_FEATURES.
- Use BitBake/OE variables (${sbindir}, ${datadir}, PYTHON_SITEPACKAGES_DIR, HOST_PREFIX, UNPACKDIR) instead of hardcoded paths, and follow the new WORKDIR/UNPACKDIR/S conventions.
- Fix reproducibility issues such as buildpaths embedded in binaries; prefer --file-prefix-map and don't install files (e.g. meson-info) that break reproducible builds.
- Make shell code in recipes and classes POSIX-compliant (avoid bashisms) since /bin/sh may be dash.
- Make ptest support actually work: create destination directories explicitly, install binaries and full test data to the documented locations, and make run-ptest produce correct pass/fail output.
- Ensure patches and code build on all supported targets (musl, mingw, clang, other architectures), not just the one tested; mark glibc-only recipes COMPATIBLE_HOST/incompatible with musl.
- Add tests for new functionality and bug fixes, gate them on architecture/tool availability, make them deterministic, and fix test bugs before resubmitting.
- Update LIC_FILES_CHKSUM when license files change and add the License-Update tag; consolidate to a single authoritative source (e.g. REUSE.toml) where it covers the project.
- Use correct upstream version metadata: tag=v${PV} and SRCREV pointing at the release tag (not a moving branch), correct sha256 checksums, PYPI_PACKAGE/UPSTREAM_CHECK_* set properly, and drop UPSTREAM_CHECK_COMMITS when tags exist.
- Set REQUIRED_DISTRO_FEATURES when a recipe genuinely needs them, inherit features_check to enforce them, and place recipes in the layer/dynamic layer matching their dependencies.
- Package every file the recipe installs (avoid "installed but not shipped" QA errors), only add existing files to FILES/CONFFILES, and add RPROVIDES when files move between packages.
- Use native tools from explicit DEPENDS (e.g. patchelf-native) instead of assuming the host or uninative provides them, and add them to the correct dependency variable for the task that needs them.
- Don't impose artificial version constraints (e.g. upper bounds on setuptools) in patches, and prefer command-line overrides over patches that change build flags.
- Handle both unset and empty variables in Python and shell code (os.getenv fallbacks, TEST_SUITES, DISTRO_CODENAME) to avoid autobuilder failures.
- Only use Python features available in the minimum supported Python version; write minimal purpose-specific code instead of pulling in new stdlib modules.
- Put CVE_PRODUCT/CVE_STATUS changes in separate patches and use status keys that exist in the target branch.
- Use the correct build-system class (setuptools_build_meta, autotools, etc.) instead of patching the upstream build backend, and use upstream's own install/test parameters.
- Don't suppress QA findings (textrel, RPATH, missing PACKAGECONFIG); fix the underlying patch or library instead.
- When removing or renaming a recipe, delete the old file and drop it from packagegroups and all other references.
- Add generated directories to the cleandirs of the task that creates them, and handle wildcard paths and pre-existing directories gracefully.
- Use shared helper functions or a shared .inc/library instead of duplicating slightly different copies across files or recipes.
- Read BitBake variables once (e.g. in setUpClass) rather than repeatedly, and use addCleanup() for test file removal, to keep parse/test times fast.
- Add sign-offs and correct authorship to all patches, fix patchtest findings and commit metadata accuracy before resubmitting.
- Use proper patches instead of sed/rm hacks in do_install, and patchdir= when patching submodules.
- Document non-obvious choices: why Inappropriate patches are carried, class usage and drawbacks, and hard requirements in the cover letter.
